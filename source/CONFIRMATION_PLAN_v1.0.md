# Confirmatory C++ kernel experiment plan v1.0

Frozen before confirmatory timing. Date: 2026-10-25 (Asia/Shanghai). This plan does not treat the earlier 100k pilot or 1M calibration as confirmatory evidence; those outputs were inspected and informed measurement setup. It makes no predicted direction or minimum speedup claim.

## Question and scope

For a fixed input stream, does replacing scalar threshold checks with an AVX2 batch threshold filter change end-to-end streaming top-k selection time for either a bounded min-heap or a sorted contiguous array? How does the measured effect vary across three continuous IID distributions and one chronological application-derived stream? This experiment concerns the controlled C++ kernels in `kernels.hpp`, not end-to-end PostgreSQL, DuckDB, Lucene, ClickHouse, or Velox performance.

## Fixed workloads

All inputs have N=1,000,000 finite float64 values. Synthetic datasets are seeded, unshuffled IID draws generated by `data.py`: `data/uniform_1000000_s45.csv` (seed 45, Uniform[0,1)), `data/normal_1000000_s43.csv` (seed 43, standard Normal), and `data/pareto_1000000_s44.csv` (seed 44, Pareto(alpha=2)). The real-data stream is `data/nyc_yellow_2024_01_distance_chrono_1000000.csv`, the first one million qualifying `trip_distance` values from NYC TLC Yellow Taxi 2024-01, ordered by pickup timestamp and source-file position; it is chronological, duplicate-rich, and not IID. Exact dataset and source hashes are in adjacent JSON manifests. Two retention sizes are tested: k=100 (k/N=0.0001) and k=10,000 (k/N=0.01). No other k, N, or distribution is part of this confirmation.

## Methods

Run all seven implementations: `heap_scalar`, `heap_batch`, `heap_avx2`, `array_scalar`, `array_batch`, `array_avx2`, and `stl` (`std::partial_sort_copy`). The two primary treatment contrasts are `heap_scalar` versus `heap_avx2`, and `array_scalar` versus `array_avx2`. The batch scalar filter is a secondary implementation control; STL and heap/array comparisons are contextual secondary comparisons. No claim that these compact kernels are a source-equivalent implementation of the industrial systems is tested here.

## Procedure and independent unit

For each of the 8 dataset-by-k cells, collect 25 process blocks. Every process loads the same hash-verified input, computes a reference result outside the timed region, performs one correctness-checked warmup, then records 5 separate calls. The process block is the independent unit; the 5 calls are repeated measurements nested within a block. Use each run's median call time as the block observation. Randomize method order independently within each block using the recorded seed. Pin child processes to logical CPU 2. Do not stop early, extend a cell because of its observed effect, or replace runs based on timing direction. Preserve failed runs and rerun a whole block only for a documented technical failure, retaining both original and replacement records.

The primary timing is complete C++ selection call time, including state initialization, input scan, and ordered output production. It excludes CSV loading, reference sort, warmup, correctness comparison, checksum, and process startup. Check output equality and checksum on every run. This is a single-host WSL2 result on AMD Ryzen 9 PRO 7940HS, GCC 11.4.0/libstdc++ 11, AVX2; it does not estimate portability across CPUs or compilers.

## Outcomes and analysis

Primary effect per cell is the geometric mean of paired process-block ratios `scalar_time / avx2_time`; values above 1 favor AVX2. For the 8 primary contrasts, compute 99.375% percentile bootstrap intervals from 100,000 resamples of paired blocks (fixed RNG seed); these are nominal Bonferroni-adjusted intervals across 8 comparisons, with approximate simultaneous 95% coverage. Call a cell's timing evidence consistent with a difference only if its interval excludes 1; report both directions and all intervals, including null or adverse results. No additional sample collection is triggered by interval position. Also show block-level observations and raw repetitions. Batch/scalar, heap/array, and STL comparisons are descriptive secondary outcomes, not post-hoc primary claims.

Separate diagnostic builds/calls collect visits, prefilter passes, actual replacements, and batch counts; they are not timed evidence. Separate gated `perf stat` runs will collect cycles:u, instructions:u, branches:u, and branch-misses:u for each method/workload/k cell, with ten calls per method per cell. Counter runs are diagnostic and not mixed with timing. Report event running percentages and denominator-aware aggregate rates; do not attribute aggregate branch misses to one source branch, equate counts with time shares, or infer zero stalls. Static disassembly is descriptive only.

## Stop conditions and reporting

Stop a cell on any correctness/checksum mismatch, dataset or binary hash mismatch, AVX2 unsupported error, perf event failure, or resource exhaustion; preserve logs and report incompleteness. Do not drop statistical outliers. Report any machine contention, thermal/frequency uncertainty, or run failures. Results support only the specified workload/host/compiler scope. Preserve exploratory and confirmation outputs separately; never overwrite them.

## Frozen environment

Before starting, save SHA-256 of this plan and of `bench.cpp`, `kernels.hpp`, `build/topk_bench`, and `run_pilot.py`; save compiler/libstdc++ version, CPU flags, `lscpu`, CPU affinity, input hashes, exact commands, and random seeds with outputs. If kernel code or data changes, stop and create a new plan version before further confirmatory measurements.
